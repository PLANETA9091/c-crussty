## Рефутация «topup-фикс как S-рычаг» (стат-мат, pop150k leg 9000s @20TPS = 180k т)

1. **SCAN-READ** (TOPUP-SCAN каждые 120т = 1500 сканов/лег, w.getEntities() O(148k)):
   25-100 нс/ent → 3.7-14.8 мс/скан → **5.5-22 с/лег = 0.06-0.25% wall**.
   Плюс alloc-чёрн ArrayList 148k×8B ≈ **1.78 ГБ/лег** (minor-GC давление, ≤0.5%).
2. **DRAIN-CHURN** (сцена-by-design, S7-147 канон): равновесие item-лейна =
   plan 105k items / lifetime 6000t = **17.5 spawn/тик → 3.15М dropItem/лег**.
   Каждый world.dropItem = полный addEntity-путь (C61: 23% addEntity + 32%
   containsKey на Wedge-кейсе). При 200-400 мкс/спавн = 630-1260 с = 7-14% wall.
3. ВЫВОД: бакет «command-context 49.8%» / «харнес-скан 23.3%» (AG-209/AG-226) —
   атрибуционная каша: scan-read ≈ 0.1-0.8% wall, доминирует **drain-чёрн =
   намеренная сцена**, не харнес-такс. Потолок «49.8%» как исправляемая
   харнес-плоскость — **REFUTED-grade**: исправляемая часть ≤1-2% wall << бар 20пп
   (кросс-раннер σ_d ~12пп, AG-210/212 — даже 2% несудим n=1).

  topup не стрелял @TPS 0.7). Real-count полный скан 120т = **сеймотика
  безопасности**, не бухгалтерия.
- Rotation-скан (K батчей, staleness ≤480т): bias +2.8% фантом-дефицита
  (17.5/t decay × 240t средний staleness) → переспавн → сцена тяжелее плана →
  measurement-semantics drift; в slow-TPS режиме детекция дренажа замедляется 4×
  именно там, где S7-147 она спасала.
- Event-каунтеры (EntityRemoveEvent): drift при пропуске cause (merge/out_of_world),
  тихая порча фикстуры. Запрещено.
