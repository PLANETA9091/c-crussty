  retransform-on-live-class — race between the poller's force-load/retransform
  kicks (attempts 2-4 all succeeded) and the first Server-thread noise call, or a

## ADDENDUM (S7-6, same day 20:2xZ) — P0 ROOT-CAUSED & CLOSED

Decisive experiments (armed = `CRUSSTY_NATIVE_IMPROVED_NOISE=1` everywhere):

| Boot | module .so | runtime .so | Result |
|---|---|---|---|
| 19:54 crash | d92ed5a0 (old) | pre-19:58 build | **SIGSEGV pc=0x0 in `dev.crussty.hooks.SchedulerHooks.onTick()V (native)`, Server thread `_thread_in_native`, ~25s post-Done** (hs_err_pid18761; launcher exit 134=SIGABRT) |
| 20:09 armed | d92ed5a0 (old) | redeployed 19:58:42 | healthy: pristine sighting EARLY (pre-force-load), hook serve+armed post-Done, alive 90s+, 0 new hs_err |
| 20:18 armed | HEAD 0c1291c1 (TASK-43 included) | redeployed 19:58 | hot-reload swap-in PASS + alive 75s post-reload, 0 new hs_err, noise re-armed |

Key discriminators:
- The crash boot had NO `pristine sighting` / `hook serve` / `hook armed` lines at all — the byte-hook
  pipeline died before the class was ever captured; the healthy boot's hook chain ran end-to-end.
- The module .so was IDENTICAL in crash vs healthy-20:09 boots (d92ed5a0) → the module was NOT the
  variable. `libcrussty_runtime.so` was redeployed by the other session at 19:58:42 (between the
  crash and the healthy run) — built from their WIP that became TASK-43 (11b19c3, committed 20:03).
- TASK-43 D4 comment names the exact mechanism: `find_class` CACHE lock `.unwrap()` panics on a
  ClassFileLoadHook callback thread → unwind across JNI → VM abort; D3/D4-adjacent fix covers the
  3 QUEUE lock unwraps in main_thread.rs — `SchedulerHooks.onTick` (the crash frame) is the
  run_on_main_thread QUEUE drain on the Server thread. First panic poisons the lock (or kills the
  byte-hook chain), the tick-drain .unwrap() then panics on the JNI thread → abort. Panic stderr
  was lost with the truncated session boot log (console.log holds only the hs_err dump).
- 839aefc→f86c517 contains NO functional runtime change (docs + clippy only), consistent with the
  bug predating that window (the C1-era lock shape).

Verdict: **P0 closed** — armed mode is stable on current master (TASK-43) + runtime >= the
19:58:42 redeploy. The 134-exit SIGABRT-vs-hs_err-SIGSEGV mismatch is the panic-across-FFI UB
signature (Rust unwind across a JNI entry = UB; HotSpot reports the resulting wild jump as
SIGSEGV pc=0x0). Armed profiles may be re-enabled on live servers running this stack.
Deployed state after this session: modules/crussty/libcrussty.so = HEAD 0c1291c1.
