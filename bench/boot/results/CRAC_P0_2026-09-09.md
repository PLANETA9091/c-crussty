## Setup

- Platform: Azul Zulu **JRE** 21.52+203-CRaC-CA (build 21.0.12.1+1-LTS) — same OpenJDK version line as the box's Temurin (21.0.12.1). Staged `/home/z/crac-jdk` (54MB tarball, Azul metadata API URL, foreground download per setsid-bg law).

- Exit cause: **unknown** — exit code not captured (process reaped by subshell before instrumentation).

## Verdict (honest)

**P0 flag-acceptance = FAIL-as-is**: the platform boots Purpur cleanly 3/3 but the JVM **self-terminates within ≤2s of Done** under this CRaC build in this environment — unusable as a server runtime as-is. P1 (checkpoint) **unreachable** — blocked by the pre-checkpoint exit, NOT by the predicted listening-socket refusal (that kill-condition remains untested). CRaC channel status: stays **OPEN but gated** on a new blocking defect.

## NEXT (mitigation ladder, cheapest first)

1. **Capture exit code + `mkdir -p $IMG` before boot** — `CRaCCheckpointTo` pointed at a non-existent directory is the top suspect for a CRaC-patched lazy-init abort; exit code discriminates clean `System.exit` vs signal.
2. Full **JDK** variant (not JRE) of Zulu CRaC 21 — JRE packaging is the second suspect (trimmed jcmd/jdk.crac internals).
3. If 1-2 fail: `-XX:CRaCCheckpointTo` unset boot (pure CRaC-JRE-without-flag) isolates whether the flag itself triggers the exit.
4. If still dying: channel downgraded to BLOCKED-environment; re-probe only after a CRaC build change.

## Lessons (class: probe hygiene)

- 5th instance of the silent-background family: my probe's own background subshells held the tool stdout pipe → 300s tool-call timeout despite the script finishing its logical path; redirect/detach ALL background fds, not just the server's.
- Liveness monitor (2s sampling from Done) is the pattern that turned "process mysteriously gone" into a bounded survival window — reuse for any flaky-exit probe.
