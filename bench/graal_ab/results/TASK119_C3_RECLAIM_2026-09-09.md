## Design

agent env-unset, G1 2G — the SOAK-PASS config), single arm vs its own PAIRED
baseline (correct choice: absolute RSS varies ~±10% across boots here, so
cross-boot normalization would drown the signal), n=3 independent boots.
Per boot: fresh seed restore -> boot -> idle settle -> R0 -> forceload add

each boundary. 3200-band chosen far from spawn: no viewer tickets, so
removal actually releases the chunks.

## Interpretation

C3 closes the loop TASK-117 left open: the forceload-resident working set
behaves as BY-DESIGN accumulation in BOTH directions — it accumulates while
held (soak: live max ~1021M ≈ 2560 resident chunks) and RELEASES on removal
(this probe: live set back to baseline occupancy, resident RSS within 10% of
baseline, no forced GC needed). The TASK-117 rss-growth INVESTIGATE trigger
firing 7/7 was correctly diagnosed as mis-specified for accumulating
patterns, and the D1 override is now backed by direct reclaim evidence
instead of inference. Operator guidance update: for workloads that
forceload-and-release, no action is required; if a future workload shows
resident RSS that does NOT return after release, the FAIL leg of this
decision tree (jcmd GC.run => histogram) is the standing investigation
protocol.
