## Design

One variable per A/B (TASK-116 law). A = operator-of-record config (GraalVM
CE 21.0.2 + -XX:+UseJVMCICompiler + production runtime agent env-unset,
G1 2G — the TASK-117 SOAK-PASS config); B = A + -XX:+UseStringDeduplication.
Warm ABBA n=3/arm, 3200-band 64-chunk bursts, seed restore every run,
J0 burst CPU law, gc.log per run. Honest scope (pre-registered): dedup win
class is HEAP (JEP-192 13.5% dup-strings claim is generic); worldgen strings
are mostly transient, so prior expectation was weak-to-neutral — this was a
cheap measured A/B, not a code change. Cold pass not applicable (dedup barely
acts in a cold window).

## Result: NULL — flag NOT adopted, operator config UNCHANGED

| arm | cpu_burst med | t_burst med | rss med | max-pause med | all cpu |

| B +dedup   | 29.6s | 25.1s | 1305MB | 114.7ms | 29.2/29.6/29.8 |

- cpu delta: **+3.9%** (wrong direction; gate needs >=3% DOWN)
- rss delta: **+9.0%** (worse — no duplicate-string population to compress,
  dedup thread + table overhead only)
- max-pause delta: **+32.0%** (violates the <=20% regression gate outright)
- FULL separation: every B run worse than every A run on cpu.

## Interpretation

Mechanistically coherent three-way negative: on a 2-vCPU box with a
worldgen-shaped workload, G1 string deduplication has no duplicate-string
population to amortize against (transient young-gen strings never reach the
dedup candidate pool), while its background thread and string-table work cost
real CPU and pause time. The JEP-192-style heap win does not transfer to this
workload class. Cheap A/B did its job: candidate measured, honestly killed,
zero code touched.
