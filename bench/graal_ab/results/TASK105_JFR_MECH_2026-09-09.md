## 1. Question

TASK-100 measured that armed native noise kernels (PerlinNoise.getValueWholeBody
+ ImprovedNoise.noiseWholeBody via libcrussty bridge) cost **+35% CPU on
JIT-warm bursts** (full separation under both C2 and Graal, 6v6 exact p≈0.001),
while the same kernels WON -11.1% on cold bursts (TASK-74). The regime split was
hypothesized (inlining barrier: warm C2 inlines the whole noise call → bridge
per-call overhead loses; cold → bridge skips giant-method compilation → wins)
but not profile-proven. This task confirms or refutes the mechanism with JFR.

## 5. Refined mechanism — three additive layers, all directly evidenced

1. **Per-call bridge overhead (Java-visible).** `PerlinNoiseNativeOps.handle` /
   `.getValue` appear as separate, non-inlined Java frames in armed runs
   (1.1-1.6% of samples; the class is never on-stack in dormant, where C2 has
   inlined the entire ImprovedNoise/PerlinNoise body into doFill callers —
   dormant profiles show noise math as anonymous heat inside
   `DensityFunctions$Ap2`/`NoiseChunk` callers). The striped identity-map
   lookup surfaces as elevated `Objects.hashCode` (2.1% vs 0.5-0.7%).
2. **Native Rust execution time.** `jdk.NativeMethodSample` catches the
   worldgen worker (`Paper Common Worker #0`) in native code 22-25 times per
   burst in BOTH armed runs and NEVER in dormant. Native time is invisible to
   `jdk.ExecutionSample` — this explains the Java-sample inversion (armed 564-
   640 vs dormant 702-729 samples despite equal-or-longer burst windows): part
   of the armed CPU is Rust time that Java profiling cannot attribute.
3. **GC pressure.** Burst-window GC: armed 6/1549ms and 8/2169ms vs dormant
   5/1175ms and 7/1888ms — **+1 pause and +281/+374ms in both pairs**,
   consistent with double[] marshalling and handle lifecycle per call.

Mechanism chain validated against the regime model: on a warm burst C2 has
inlined the whole noise method, so the bridge is pure regression (layers 1+2+3
all add cost); on a cold burst the bridge skips compiling the 11k-byte giant
method and compile-avoidance dominates. Both sides of the regime boundary now
have direct profile evidence, not just CPU deltas.

## 6. Consequences

1. **PROMOTION FREEZE stands, now profile-grade.** Freezing armed live wiring
   for warm servers was based on CPU separation; it now has mechanism-level
   attribution. No further freeze-relevant A/B needed.
2. **Concrete re-open engineering requirement**: a **batch/array bridge** —
   one JNI call per fill-array operation (whole-column/whole-cell), amortizing
   marshalling, map lookup, and handle lifecycle across N values — removes
   layer 1 and shrinks layer 3; layer 2 (actual Rust kernel speed) then
   competes on merits in the warm regime. Per-value JNI calls are dead for
   warm servers regardless of kernel speed.
3. **New candidate line (unbanked observation)**: `SimplexNoise.dot` is a
   pure-Java leaf at 5.4-6.2% in ALL FOUR arms (not covered by the armed
   kernels). Any future SimplexNoise kernel must be batch-bridged from day one
   and must pass the warm-regime P500 protocol from TASK-100 §4.
4. Harness lesson banked: dynamic `jcmd`-scoped JFR windows (start/dump/stop
   around the measured burst) give clean regime attribution without boot/warm
   pollution; `jdk.NativeMethodSample` is the tool for measuring Rust-side
   occupancy that Java sampling cannot see.
