## 1. Flag archaeology on the deployment JDK21 (product VM, /home/z/jdk21)

The research item named `-XX:HugeMethodLimit`. Measured on our JDK 21:

```text
$ java -XX:+UnlockDiagnosticVMOptions -XX:HugeMethodLimit=65535 -version
Error: VM option 'HugeMethodLimit' is develop and is available only in debug version of VM.
```

**HugeMethodLimit is develop-only on JDK21 product builds** — the literal research
prescription is not executable in production. The action path that DOES exist:

```text
$ java -XX:+PrintFlagsFinal -version | grep -i huge
     bool DontCompileHugeMethods                   = true     {product} {default}
$ java -XX:+UnlockDiagnosticVMOptions -XX:-DontCompileHugeMethods -XX:+PrintFlagsFinal -version | grep DontCompile
     bool DontCompileHugeMethods                   = false    {product} {command line}
```

`DontCompileHugeMethods` (product, default true) is the gate: when true, methods
above the internal HugeMethodLimit (**8000 bytecodes**, non-writable default on
product) never reach C2. Flipping it to false allows huge methods to compile.
The Twitter/Netflix-era JVM-tuning lore behind the TASK-83 GO maps onto this
flag, not onto HugeMethodLimit itself.

## 3. Dynamics: why the flag-flip is null by construction on this workload

The gate only matters for a huge method that gets *hot enough to compile*.
First compilation under tiering requires Tier3InvocationThreshold = **200
invocations** (measured on our JDK21: `Tier3InvocationThreshold = 200 {product
{default}}`; legacy `CompileThreshold = 10000`). Every one of the 16 methods is
invoked a handful of times at most (once for &lt;clinit&gt;/datagen; the BlockStateData
bootstraps run once during DataFixer construction each boot). They never cross
200 invocations, therefore they stay interpreted **regardless of the flag**.
Flipping `-XX:-DontCompileHugeMethods` changes nothing observable — there is no
hot huge method for it to admit into C2. (If anything did compile, it would be
a boot-once 9–59 KB body where C2 compile CPU exceeds the interpreted single
execution by orders of magnitude — a pure loss; DontCompileHugeMethods=true is
the correct default precisely for this population.)

A live boot A/B would therefore measure noise by construction. Per the
census-first discipline (falsify cheaply before expensive measurement) the
task closes here with zero boots spent.

## 4. Verdict

**TASK-85 JIT-heuristics channel: MEASURED (static) NO-GO / DO-NOT-FLIP.**
The TASK-83 GO is corrected on two grounds: (1) the named flag HugeMethodLimit
is develop-only on JDK21 product (prescription unexecutable as written);
(2) the executable knob DontCompileHugeMethods=false has an empty hot-path
surface on this workload — full-jar census shows only cold single-shot methods,
and tiering thresholds make the flag a no-op for them. This closes the
JIT-heuristics branch of the x1000 hunt at the static layer — the cheapest
refutation in the ledger (0 boots, 0 bench infra, 0 src/ changes).

**Re-open criteria:** a future Minecraft/Paper version introduces a method with
Code.length &gt; 8000 on a measured-hot path (re-run the scanner; it costs
seconds). The scanner ships in this directory for exactly that check.
