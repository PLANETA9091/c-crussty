## База и метод

`updateFluidHeightAndDoFluidPushing`, под-лейны по ЛИСТУ) и
`scripts/bench4_recon/recon42_rerank_leaf.py` (каждый java-сэмпл считается ровно один раз
по листу — устраняет double-count regex-подхода RECON-41).

## Поправка RECON-41: точный размер лейна n-push

RECON-41 мерил лейн regex-ом `Fluid|fluid` по всему стеку → захватывал чужие стеки с
FluidState (collision/travel/рандом-тики). Точное измерение по вход-пути скана:
**n-push = 14.6% java-сцены** (15319/105003 @ s7201; 15510/106479 @ s7203 — идентично),
а не 23.6%. Следствие: настоящий ТОП-1 стека-атрибуции под ParallelGC — именно
**volatile/inside 13.2%** (атакуется #15 в полёте) — атака по адресу.

## Вердикт-1: лейн n-push ЗАКРЫТ (10-е док-закрытие, класс RECON-17/20/38)

1. **Однородного под-лейна ≥5% java нет**: максимум — self-оркестрация скана 3.40% java
   (пер-блочный цикл + floor + AABB-математика), далее чтения 2.08%. Крупнейшая семья
   «оркестрация» ≈4.8% (self + floor 0.32% + AABB 0.21% + setDeltaMovement 0.45% + аллок-хвост)
   — всё равно <5% и парити-заперта: скан per-entity-per-tick из baseTick — ванильная
   семантика; пропуск/режиж скана = парити-брейк (запрещённый класс).
2. **Чтения (5.1–5.3% java суммарно) = REFUTED-зона**: RECON-35/38 закрыли семью
   memо/диет-атаками (6 ног, 0% TPS-конверсия, потолок <7.6%); правило
   REFUTED-не-закрывает-лейн отработано свежим RECON — под-лейн подтверждён тем же
   рефьюзом на новой экономике, нового однородного ≥5% угла нет.
3. FLOW 0.8% / SAME-ABOVE ~0% / AABB 0.4% — хвосты <1%, не реализовывать (правило <5%).

## Гейты/ограничения

- Оба профиля — ноги банка v4 (валидные SUCCESS-леги с pop-VALID), атрибуция leaf-based
  воспроизводима одной командой; разброс под-лейнов между ногами <0.2пп = статистика устойчива.
- Вердикт не зависит от исхода #15: даже при CRASH/rollback n-push остаётся закрытым
  (потолок <10%), а ранк ТОП-1 сохраняется.
