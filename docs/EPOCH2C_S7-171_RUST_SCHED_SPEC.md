## 1. Тезис эры

Полное картирование сцены (RECON-25..35: 9 док-закрытий + 6 REFUTED-рычагов) доказало:
однородного Java-лейна ≥5% с ДВОЙНЫМ БАРОМ на текущей архитектуре НЕТ — вариант A
исчерпан полностью. C растёт НЕ сокращением CPU, а WALL-CLOCK параллелизмом: перенос
фаз тика с критического пути MSPT на worker-потоки (Амдал: сокращение serial-остатка).
C — единственный путь качественного (не процентного) роста TPS на X150K. Гейты эры
остаются ДВОЙНЫМ БАРОМ: C по определению атакует TPS, а не только min-MSPT.

## 4. Архитектура (M1-first)

- **M1 «упорядоченная параллельная оценка»** (выбран): dependency-анализ тик-листа;
  параллельно исполняются только сущности без общих наблюдаемых состояний;
  слияние эффектов В ИСХОДНОМ порядке на границах секций (ordered commit).
  Median-exact сохраняется структурно, а не эмпирически.
- **M2 «спекуляция + коммит в исходном порядке»** — отложена (высокий парити-риск,
  пересмотр после зелёного M1).
- **Владение**: Rust-планировщик владеет снапшотом тик-листа (прецедент
  entity_mirror) и планом секций/барьеров; Java исполняет лист-работу; JNI-переходы
  амортизируются батчингом (прецедент batch_api/batch_collector).
- **Граница состояния**: block-writes и спавны/деспавны — только через ordered
  commit-очередь на главный поток; чтение чанков — существующая конкурентная карта
  ServerChunkCache (RECON-31: acquire-семантика обязательна, снятие запрещено);
  RNG — serialized per-source (прецедент S7-158d RngOps); mid-tick pumps — режим
  suppression/репродукции (прецедент S7-157b).

## 5. Парити-модель и оракул порядка

- Инвариант: median-exact порядок наблюдаемых эффектов (setBlockState,
  randomTick, spawn/discard, entity-мутации видимые соседям) = ванильному
  последовательному тику при любой конфигурации workers.
- Оракул: локстеп-харнесс ПОРЯДКА — снапшот сцены → (a) ванильное ядро,
  (b) C-ядро; сравнение последовательности observable-эффектов (не только
  конечного состояния). Контракт харнесса прегистерится ДО P2 (шаблоны:
  v2a ×29, #15 1M-кейсов). Честный резидуал фиксируется в контракте
  (живые chunk-map/debug/effects-потоки = гейты CI-лега, прецедент #15).

## 6. Фазовый план (каждая фаза = коммит-пригодные тики)

- **P0 = эта спека (S7-171)** — открыта; диспатча нет.
- **P1: RECON-36 serial-fraction** — измерение serial-остатка (барьеры/оркестрация/
  main-only фазы из свежих профилей + javap-контракт RegionTickOps.tickBucket/
  midTickTasks/барьеров) + конфликтная матрица состояний entity-tick (что читает/
  пишет каждая фаза) → вердикт-док с числами и финальной оценкой потолка.
  Гейт: если serial-fraction > 70% сцены — C-эра ПАУЗА с вердикт-доком (Амдал убивает).
- **P2: M1-прототип на ограниченном классе** — ItemEntity первым (наибольший
  счётчик сцены, простейшая семантика мутаций); оракул порядка green обязателен
  до любого CI-лега; фоллбэк каждого сплайса — ванильный путь (fail-closed).
- **P3: CI-лег s7196+** — dispatch по канону dispatch_s7189.py (изоляция:
  банк v3 + scheduler=1, широкий банд 6.0..9.5M, S7-108 гварды, commit/push

- **P4: экспансия** — Mob → полный bucket → off-thread world-tick фазы
  (block/fluid/random ticks) по мере зелёных оракулов; каждый шаг = свой лег.
