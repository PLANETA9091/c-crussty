## 1. g9 `DensityAp2MinMaxFill` — PRODUCTION SITE FOUND

### 1.1 Identified mirror

The min/max density fill loop is the **MIN and MAX arms of
`net.minecraft.world.level.levelgen.DensityFunctions$Ap2.fillArray([Lnet/minecraft/world/level/levelgen/DensityFunction$ContextProvider;)V`**
(vanilla `final class DensityFunctions$Ap2 extends Record implements TwoArgumentSimpleFunction`; fields `type`, `argument1`, `argument2`, `minValue`, `maxValue`).

This resolves the task-context hint precisely: the NoiseChunk-adjacent classes (`NoiseChunk`, `NoiseChunk$NoiseInterpolator`, `NoiseChunk$CacheAllInCell`) are the *reachability path*, but they hold `double[][]`/`double[]` slices and delegate; the actual min/max fill loop lives in `DensityFunctions$Ap2` (the "Ap2" of the kernel name). The sibling kernel g8 `DensityAp2Fill` (symbols `oldFlat/oldNested/scratchFlat/scratchNestedSummary`) shadows the ADD/MUL arms of the same method — one vanilla method, two P500 groups.

### 1.3 Feasibility verdict (honest)

- **What the site is:** a real, hot, per-chunk-generation loop (`fillSlice` runs 1+cellCountXZ times per chunk — 5 for the overworld cellWidth=4/cellCountXZ=4 — each calling `NoiseInterpolator.fillArray` per Z-column over a cellHeight×cellWidth²-element slice; `Ap2.fillArray` then runs per fill over the full array with a virtual `compute()` per element). The adoption matrix's S2 model (192 section-fills/tick, `:96`) is order-of-magnitude consistent with this topology.
- **Variant R (same-descriptor invokestatic retarget) is NOT applicable.** There is no kernel-shaped `invokestatic` anywhere in the chain: the fill loop is composed of `invokevirtual`/`invokeinterface` (`fillArray`, `compute`, `minValue/maxValue`) plus `Math.min/max` statics. A same-length CP-operand retarget has nothing to match on.
- **The viable mechanism is the one the matrix already names** (`docs/BATCH_ADOPTION_MATRIX.md:110`): byte-hook on the section fill loop via the **area_map pattern** (whole-method body replacement = `patch_update`/REPLACE_BODY + loader-local helper + 64-case selftest + env gate), target method = `DensityFunctions$Ap2.fillArray([LContextProvider;)V` (finest grain, MIN+MAX arms) or `NoiseChunk.fillSlice(ZI)V` (chunk-grain driver). The native body must reproduce the `minValue()/maxValue()` short-circuit branches (`dcmpg`/`dcmpl`) to stay semantics-identical.
- **Batching economics unchanged:** at 119.8 ns direct vs the measured dispatcher fixed ≈205 ns + ≈40 ns/op marginal (G4 §1), the batch does not win today — this candidate ships dormant and stays a whole-method-hook design, not a batch-dispatch consumer. The `(III[J)I` kernel remains the shape-compatible *calibration* of the hook body, not a drop-in retarget.
- **Honest unknown:** the semantic mapping of the kernel's 3 int scalars onto production values is not documented anywhere in the repo (stub is synthetic; `gen_p500_bench.py` has no mirror table). Class/method identity is certain; scalar semantics are inferred.

**Verdict: SITE FOUND — `DensityFunctions$Ap2.fillArray` MIN/MAX arms (reachability `NoiseChunk.fillSlice` → `NoiseChunk$NoiseInterpolator.fillArray`). Candidate 2 unblocked for the *whole-method byte-hook* design; NOT eligible for Variant R retarget; dormant until JFR amplification proof per matrix.**

## 2. g42 `StaticCacheGet` — PATTERN SITE FOUND (retarget infeasible)

### 2.1 Identified mirror

`net.minecraft.util.StaticCache2D<T>` — the vanilla fixed-window 2D chunk cache:

```
public class net.minecraft.util.StaticCache2D<T> {
  private final int minX; private final int minZ;
  private final int sizeX; private final int sizeZ;
  private final java.lang.Object[] cache;
  public static <T> StaticCache2D<T> create(int, int, int, StaticCache2D$Initializer<T>);
  public T get(int, int); public boolean contains(int, int); private int getIndex(int, int);
}
```

The kernel name "StaticCacheGet" matches this class; the "cache-get burst" consumers live in the chunk-loading/generation-status service domain (`net/minecraft/server/level/*`, `net/minecraft/world/level/chunk/status/*`) — this matches the "kernel-svc" domain label. Constant-pool grep over the extracted jar (9,809 class files, `rg -a "net/minecraft/util/StaticCache2D"`) lists the complete user set: `GenerationChunkHolder`, `GeneratingChunkMap`, `ChunkGenerationTask`, `ChunkMap`, `WorldGenRegion`, `ChunkStatusTask` (+ `StaticCache2D$Initializer`). No other users exist in the live jar.

### 2.3 Feasibility verdict (honest)

- **What the site is:** real bursts — per chunk-generation task, `scheduleLayer` walks up to `(2r+1)²` cache-gets per status layer (16 layers to FULL; r = accumulated radius from `ChunkPyramid.GENERATION_PYRAMID`), plus per-position gets via `WorldGenRegion.getChunk` from arbitrary worldgen code. This is the production analog of the g42 kernel's burst shape (int keys in, results out).
- **Variant R same-descriptor invokestatic retarget is NOT applicable — twice over:**
  1. Every production get is `invokevirtual net/minecraft/util/StaticCache2D.get:(II)Ljava/lang/Object;` — a virtual call on a generic Object-returning method followed by `checkcast`, not an `invokestatic` with a primitive-long descriptor.
  2. The result is consumed as an **object ref** (`GenerationChunkHolder` → `scheduleChunkInLayer` / `getPersistedStatus` / `acquireGeneration` identity). The kernel's `(IIIII[I[J)I` shape packs results into a `long[]` — it cannot carry the vanilla object identity a consumer requires, so even a whole-method rewrite of `scheduleLayer` would need an object-returning batch get, not the shipped shape-C kernel.
- **Branching:** `scheduleLayer` early-exits on `markedForCancellation` and the first `scheduleChunkInLayer(...) == false` (up to one full cache row before return); `canLoadWithoutGeneration` returns false on the first stale neighbor. A batched rewrite must preserve this short-circuit + try-with-resources Zone discipline.
- **Economics/policy unchanged:** wave2 matrix already grades g42 **L** ("already <40 ns — nothing to amortize", `BATCH_ADOPTION_MATRIX_wave2.md:79,185`) and the runbook verdict stands (no measured T on the closed probe body, `BATCH_ROLLOUT_RUNBOOK.md:97-103`). This recon adds the structural reason: the production call is object-returning virtual dispatch, so the shape-C kernel cannot be wired to it by any retarget variant in G4 §3.

**Verdict: PATTERN SITE IDENTIFIED — `net/minecraft/server/level/ChunkGenerationTask.scheduleLayer(ChunkStatus;Z)V` double loop over `net.minecraft.util.StaticCache2D.get(II)T` (+ `canLoadWithoutGeneration`, `WorldGenRegion.getChunk`, `ChunkStatusTasks.full`), but the production get returns object refs via invokevirtual: candidate 3 is NOT unlocked for same-descriptor retargeting, and the batch kernel cannot substitute for the object-identity consumers. g42 stays the dispatcher-calibration kernel (wave-1 framing); no wiring path exists today.**
